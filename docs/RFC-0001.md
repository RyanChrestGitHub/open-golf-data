# RFC-0001 — Event preservation, installation context and attribution

**Status:** Proposed; synthetic implementation only. **Decision owner:** Project maintainer.

## Product invariant

Any supported, authorized launch-monitor source should be able to return its accessible observations to the correctly identified golfer, with source fidelity and full portable export. An operator may enable this for home or visiting golfers. The operator of an installation does not automatically own the golfer's cross-installation history.

## Events are primary

A physical attempt, device capture, simulator shot and scored stroke are not guaranteed to be identical. Therefore the ledger's primary immutable entity is `Observation`, not `Shot`. An observation is the opaque native payload plus source ID, timestamp, version, and optional participant evidence. Semantically interpreted measurements are independent annotations.

Future `EventAssociation` records will connect events to the same physical attempt, with method, confidence, evidence and revision history. They cannot replace the original observations. Do not assume timestamp-nearest is identity proof.

## Minimal entities

- **Installation:** Source software running on an administered computer; `home` and `facility` are configuration modes.
- **Session:** An installation-scoped capture interval; not necessarily a simulator round.
- **Observation:** Immutable source event, native bytes, SHA-256, source ID/version, timestamp, optional source participant, and separately interpreted metrics.
- **ParticipantLink:** Explicit `(session, source_participant_id) -> golfer_id` supported by a declared identity-mapping event. In the synthetic demo, fictional confirmations simulate this. Real links will require verified accounts and consent.
- **Golfer:** Eventually a portable authenticated identity, never the same thing as a simulator profile or installation administrator.
- **Permission/Consent:** Future auditable claims controlling upload and download; not implemented in the synthetic lab.

## Data model design rules

1. Use `null`/absence to mean not available, and preserve genuine numeric zeros.
2. Metric kinds distinguish `device_reported`, `vendor_estimated`, `simulated`, `calculated`, `unknown`. `device_reported` means reported by a device; **it does not prove physically direct measurement**.
3. Keep native units and names even when no normalized counterpart exists.
4. IDs must be uniquely scoped to the source and session. Duplicate event IDs with differing content fail closed.
5. Store source raw payloads as bytes. JSON, CSV, protobuf, or binary could be valid future payloads.
6. Record clock information and timestamp sources. Wall-clock proximity alone cannot establish event association.
7. A compatibility declaration must specify model, software version, firmware where available, capture method, exposed field inventory and evidence status.

## Export contract

- Full-fidelity JSON contains each linked observation's original bytes as base64, digest, metadata and interpreted metrics. The native payload is included as JSON only where parsing is possible.
- CSV includes a record per observation and raw base64 payload so no source field is lost merely because it lacks a flattened column.
- Any hosted export/API must authorize access using verified identity and consent before filtering and returning data; the CLI's local `golfer_id` parameter is **not** authorization.

## Major unresolved design decisions

- Real authentication authority (OIDC provider, account linking, recovery).
- How installation-local source participant IDs are proven to belong to signed-in golfers.
- Operator custody/retention of unclaimed guest observations and consent revocation.
- Event association rules for device-vs-GSPro pairs.
- Encryption, key management, deletion and export portability for a hosted service.
- Adapter sandboxing, vendor licensing and software update safety.

These are explicit next research and engineering tasks, not capabilities established by this RFC.
